# C3S Production Rollback Plan

Rollback is version restoration and write containment, not data deletion.

1. **Declare and contain:** name the incident commander, pause operator mutations via the deployment feature flag/configuration boundary, and if necessary deploy emergency deny-write rules while retaining authorized reads.
2. **Frontend:** restore the last approved web/native artifact. Do not rebuild from an unpinned working tree. Confirm its schema/rules compatibility before reopening writes.
3. **Functions:** redeploy the last approved Functions artifact. Retain idempotency receipts and audit events; do not delete events generated by the failed version.
4. **Rules:** restore the last approved rules file from version control. Never relax rules merely to make an incompatible client work; keep writes paused until versions align.
5. **Feature flags:** disable secure transitions, delay persistence, handoff notes, or other affected flags only when the fallback client/rules combination is known compatible. Training tools remain disabled.
6. **Indexes:** normally leave additive indexes in place. Remove only after compatibility review; index rollback is not an incident write-containment mechanism.
7. **Schema:** new optional fields (`version`, `actorId`, receipts) are backward-compatible. Do not delete them. If a required-field change is implicated, deploy a compatibility reader before restoring writes.
8. **Validate data:** compare affected item status/stage, linked legacy records, equipment ownership, alerts, holds, receipts, and audit events. Record corrective events instead of rewriting history.
9. **Resume:** reopen mutations by role and workflow in staging first, then obtain explicit production approval.

## Stopping writes

Preferred order: disable mutation feature flags/configuration, remove affected UI actions, then deploy narrowly targeted deny-write rules. For a severe integrity event, deploy a global authenticated-write deny rule only with an incident owner and a tested read-only operations procedure.
